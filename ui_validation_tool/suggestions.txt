That’s expected — and it’s actually the core failure mode of naïve agentic lineage extraction.

You’re hitting the point where the agent can see I/O calls, but cannot resolve variables to concrete table names. The fix is not “better prompting” alone — you need symbol resolution + partial execution reasoning before the LLM step.

Below is a practical, battle-tested way to move from variables → real tables.

1. Why your agent returns variable names

Example:

target_table = f"{env}.{schema}.{table}"
df.write.saveAsTable(target_table)


Your agent reports:

WRITE → target_table


Because:

LLM sees symbols, not values

Values are:

Defined elsewhere

Loaded from config

Passed via job parameters

Computed at runtime

LLMs cannot guess values safely.

2. Correct solution: 3-layer resolution pipeline

You must separate extraction, resolution, and inference.

Code → Symbols → Resolved Values → Lineage

Step 1: Load and normalize configs (CRITICAL)

Support:

Environment overlays

Defaults

Inheritance

Perfect — that’s an important detail, and it changes the design slightly but cleanly.

When sources and targets can be ADLS paths, the goal is no longer “tables only” but “data assets” (tables + file paths). Your agent must treat paths as first-class lineage entities, not as a fallback.

Below is a clear, production-grade way to handle this without losing accuracy.

1. Expand the lineage model (table ≠ only asset)
Unified asset schema
{
  "type": "TABLE | FILE",
  "identifier": "string",
  "format": "delta | parquet | csv | unknown",
  "confidence": "HIGH | MEDIUM | LOW",
  "evidence": "string"
}


Examples:

TABLE → prod.sales.customers

FILE → abfss://raw@datalake.dfs.core.windows.net/customers/

2. Deterministic detection (NO LLM)
2.1 Table reads/writes
spark.table("db.schema.table")
df.write.saveAsTable("db.schema.table")

2.2 ADLS reads

Detect:

spark.read.format("delta").load(path)
spark.read.parquet(path)
spark.read.csv(path)


AST extract:

{
  "operation": "READ",
  "type": "FILE",
  "path_expr": "raw_customer_path"
}

2.3 ADLS writes
df.write.format("delta").mode("overwrite").save(path)
df.write.parquet(path)

3. Config-driven path resolution (critical)

Example config:

storage:
  raw:
    container: raw
    account: datalake
    customers: "abfss://raw@datalake.dfs.core.windows.net/customers/"


Resolve to:

{
  "raw.customers": "abfss://raw@datalake.dfs.core.windows.net/customers/"
}


Now your agent sees:

WRITE FILE → abfss://raw@datalake.dfs.core.windows.net/customers/


Not raw_customer_path.

4. Safe string resolution for paths

Support:

f-strings

.format

Jinja templates

Example:

path = f"abfss://{container}@{account}.dfs.core.windows.net/{folder}/"


Resolve using config keys.

⚠️ Same rule: strings only, no execution

5. Heuristics for ADLS paths (important)
Normalize paths

Treat these as the same asset:

/mnt/raw/customers
abfss://raw@lake.dfs.core.windows.net/customers


Store both:

{
  "identifier": "abfss://raw@lake.dfs.core.windows.net/customers",
  "aliases": ["/mnt/raw/customers"]
}

Format inference

If:

.format("delta") or _delta_log → delta

.parquet() → parquet

.csv() → csv

Else:

"format": "unknown"

6. LLM usage (now very narrow)

Use LLM only when:

Path is built across multiple config keys

Conditional storage selection

Indirect helper functions

Prompt example:

Given resolved config values and unresolved expressions, infer the most likely ADLS path or mark LOW confidence.
